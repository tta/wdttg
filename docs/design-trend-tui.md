## Problem Statement

`wdttg report trend` (main.rs:1216) currently prints top-N tasks/tags as ASCII
sparklines to stdout — read-once and gone. You can't scroll a long list, switch
period on the fly, change bucket size, or drill into a spike to see which
sessions made up that bucket. The trend report also only has two dimensions
(task, tag), ignoring the two signals that make wdttg unique: Eisenhower
Matrix quadrant balance over time, and split-attention (background/foreground
overlap) over time.

Every other exploratory view in wdttg is already a ratatui TUI — `timeline`,
`report history`, `review` — with consistent vim keybindings. The trend report
is the last stdout-only explorer. It should match.

## What Makes This Cool

Two dimensions no other time tracker can show, because no other tracker has
the data:

1. **Quadrant Trend.** Four rows (DoFirst / Schedule / Delegate / Eliminate),
   one sparkline each, showing how your Eisenhower Matrix balance shifts week
   over week. This is the "steering wheel" the weekly review design named at
   docs/design-weekly-review.md:38 — the gap between target and actual, made
   visible across time. Watch your Schedule quadrant climb as you protect
   deep-work mornings. Watch DoFirst spike during an incident week.

2. **Split-Attention Trend.** Rows are tasks where `overlap_seconds > 0`,
   showing how often each task ran under a foreground session. The sparkline
   is rendered in red when overlap is rising. This is the multitasking meter,
   tracked over time — "you split attention on `coding/feature-x` 4 weeks in a
   row, peaking at 6h overlap in week 3."

Combined with drill-down (press Enter on any row+bucket to see the sessions),
this turns the trend report from a glanceable summary into an exploratory
instrument: spot the spike, drill in, understand why.

**Data sources:** all four dimensions read from `SessionSplitTime` (returned
by `SessionService::get_split_times`, session_service.rs:273) — which already
carries `task_id`, `task_name`, `em_quadrant`, `split_seconds`,
`overlap_seconds`, and `start_time`. Three of the four dimensions (Task,
Quadrant, SplitAttention) compute from this single fetch. The Tag dimension
additionally needs `SessionService::get_task_tags()` (session_service.rs:814)
to map `task_id → Vec<tag>`, fetched once at TUI open. After open, all
dimension switches are in-memory.

## Constraints

- **No new runtime dependencies.** Same SQLite + Rust stdlib + ratatui +
  crossterm stack as the existing TUIs. No charting crate.
- **Terminal-native, vim keybindings.** Must match the existing TUI stable
  (timeline/history/review): j/k nav, Tab to cycle dimensions, d/w bucket
  keys, Enter to drill in, Esc/q to quit. See AGENTS.md "Navigation
  Convention" — j always means DOWN.
- **Single-binary architecture.** No daemon, no IPC. The TUI is opened by
  `wdttg report trend` and exits back to the shell.
- **stdout path must survive.** `--no-prompt` (cli.rs:12, global flag) keeps
  the existing stdout output for scripts and cron. The TUI is default; the
  stdout version is the fallback.
- **Read-only, no live period switching.** Unlike review (which edits
  targets) and timeline (which edits sessions), trend is a viewer. Period
  is fixed at launch from the CLI (`wdttg report trend 8w`); changing it
  requires re-running the command (same model as `timeline [date]` and
  `report history --period`). This keeps the UI a pure function of data
  per ARCHITECTURE.md:202 — no service handle in the TUI, no re-fetch loop.
  Bucket size (d/w) and dimension (Task/Tag/Quadrant/Split) ARE
  switchable in-TUI because they only re-bucket cached data.
- **SQLite migrations unchanged.** No schema change required — the new
  dimensions (quadrant, split-attention) are computed in Rust from
  `SessionSplitTime` data that already exists.

## Premises

1. The stdout sparkline is throwaway — you can't scroll, switch period,
   switch dimension, or drill into a spike. A TUI unlocks all four.
2. The TUI does not delete the stdout version. `wdttg report trend` opens the
   TUI by default; `--no-prompt` keeps stdout for scripts.
3. A trend TUI without new dimensions is just lipstick. The unique-to-wdttg
   dimensions — EM quadrant trend and split-attention (overlap) trend — are
   what make the TUI worth entering. They ship in the same PR.
4. The TUI's value is exploration: switch dimension, switch bucket size,
   scroll, drill into a bucket to see its sessions. Read-only — no
   editing. Period is fixed at launch from the CLI (see premise 6).
5. ~~Timezone bug in `get_date_range()`~~ — **RE-VERIFIED FIXED.**
   `get_date_range` (session_service.rs:710) already uses
   `local_to_utc_safe()` and `format_sqlite_datetime()`. The trend data is
   correct. No tz work needed in this PR.
6. **Period is a launch-time parameter, not an in-TUI cycle.** Switching
   period (4w → 12w) requires re-querying `get_split_times()` for a new
   date range, which means the TUI would need a service handle — violating
   the "pure function of data" rule (ARCHITECTURE.md:202). Drop live period
   cycling. Bucket size (d/w) and dimension ARE in-TUI switchable because
   they only re-bucket cached data.

## Approaches Considered

### Approach A: Trend List TUI (chosen)
Scrollable list TUI with four cyclable dimensions (Task / Tag / Quadrant /
SplitAttention), period and bucket switching, Enter to drill into a bucket's
sessions. Reuses `handle_report_trend`'s bucketing math verbatim. Smallest
diff that ships every premise.

### Approach B: Trend Chart with Drill-Down Panel
Two-panel ratatui layout — top half `BarChart` with stacked quadrant
proportions per bucket, bottom half detail list. ~1000-1200 lines.
Visually richest, but `ratatui::BarChart` fights narrow terminals and
stacked-bar custom rendering is fiddly. Rejected: visualization polish is
not the value; dimensions and drill-down are.

### Approach C: Trend Heatmap
GitHub-contributions-style grid — rows = tasks, columns = days, cell
intensity = time. Custom `Canvas` widget (~200 lines of rendering math).
Most visually striking, but heatmaps need many buckets (favors 12w/6m,
hurts 4w) and depart from wdttg's bars-and-lists aesthetic. Rejected as
the first cut; could be added later as an alternate render mode.

## Recommended Approach

**Approach A: Trend List TUI.** Reasons:

- Ships every premise in one PR at the lowest risk.
- Reuses bucketing logic from `handle_report_trend` (main.rs:1243-1295).
- Follows the `history_view.rs` pattern (917 lines, well-trodden
  ratatui-list idioms) — high confidence in the shape.
- The new dimensions (quadrant, split) are the value, not the chart. A
  list with sparklines per quadrant row is enough to see the balance shift.
- If A underwhelms after dogfooding, Approach B's bar chart can layer on
  without rewriting the data layer — the dimensions are decoupled from the
  renderer.

### TUI state

```rust
pub struct TrendView {
    // Data (fetched once at open, immutable for the TUI's lifetime)
    sessions: Vec<SessionSplitTime>,      // from get_split_times
    task_tags: HashMap<i64, Vec<String>>, // from get_task_tags, for Tag dimension

    // Launch parameters (fixed for this invocation)
    start: NaiveDate,
    end: NaiveDate,
    top: usize,                           // top-N cap, defaults to CLI --top (10)

    // In-TUI switchable state
    dimension: TrendDimension,            // Task | Tag | Quadrant | SplitAttention
    bucket_by: BucketBy,                  // Day | Week

    // View state
    selected_idx: usize,                  // selected row in the list
    scroll_offset: usize,
    drill_down: Option<DrillDownState>,   // Some when Enter pressed
}

enum TrendDimension { Task, Tag, Quadrant, SplitAttention }
enum BucketBy { Day, Week }

// One-step drill-down: Enter on a row immediately shows the sessions for
// that row's highest bucket. j/k scrolls sessions; h/l moves to adjacent
// buckets without leaving drill-down.
struct DrillDownState {
    item: String,                         // "coding/jira-123" or "Q1: DoFirst"
    bucket_idx: usize,                    // current bucket (mutable via h/l)
    bucket_labels: Vec<String>,           // ["week of 2026-04-21", ...]
    sessions_by_bucket: Vec<Vec<SessionSplitTime>>,  // pre-computed at drill-open
    selected: usize,                      // selected session row
}
```

**Empty data:** if `sessions.is_empty()` at open, the TUI still enters and
renders a single line: `No sessions in this period. Press q to quit.` This
mirrors the stdout path's early-return message at main.rs:1232-1235.

**No search state.** Unlike `history_view` (which has hundreds of sessions
and needs fuzzy search), the trend list is capped at `top` rows (default
10). j/k scroll is sufficient. Adding search is YAGNI.

### Render layout (single panel, drill-down replaces it)

```
┌─ Trend: Task | 8w weekly | 2026-04-21 → 2026-06-16 ────────────┐
│                                                                  │
│  coding/jira-123   ▁▂▅▇▆▄▂▁   ↑ +12%    18h 30m                │
│  meeting/standup   ▃▄▄▃▄▃▄▄    → 0%     8h 15m                 │
│  review/pr-456     ▂▃▄▅▄▃▂▁   ↓ -8%     6h 45m                 │
│  ...                                                              │
│  ──────────────────────────────────────────────────────────────  │
│  Total             ▃▄▅▇▆▄▃▂    ↑ +5%    52h 10m                │
│                                                                  │
├──────────────────────────────────────────────────────────────────┤
│ j/k move  Tab dim  d/w bucket  Enter drill-down  Esc/q quit      │
└──────────────────────────────────────────────────────────────────┘
```

For **Quadrant** dimension, the four rows are fixed (DoFirst, Schedule,
Delegate, Eliminate) and each shows the quadrant color via
`quadrant_color(&EmQuadrant)` (timeline.rs, exported at ui/mod.rs:19). The
rollup sums `split_seconds` per quadrant (the same field the existing Task
and Tag dimensions sum at main.rs:1278,1291). For **SplitAttention**, rows
are filtered to `overlap_seconds > 0`, sorted by total overlap descending,
and the sparkline renders in `Color::Red` when the row's last non-zero
bucket exceeds that row's per-bucket mean (i.e., overlap is trending up
for that specific task).

**Sparkline rendering note:** the existing `render_sparkline` (main.rs:1178)
returns a `String`, which cannot carry color. The TUI needs a
`render_sparkline_spans(&[i64], max, Option<Color>) -> Vec<Span>` variant
that emits one `Span` per bucket with the chosen color (or default for
SplitAttention rows that aren't trending up). Both renderers share the
level math: `((v / max) * 7.0).ceil()` clamped to `0..=7`, indexing
`SPARK_CHARS[0..=7]`. ASCII path keeps using `render_sparkline`; TUI path
uses the new `_spans` variant.

**Narrow terminals:** if usable width < 60 cols, the sparkline is elided
to fit (drop oldest buckets first, keep the most recent N that fit), and
the footer hint line wraps. The header truncates the date range with `…`
before truncating the item name column. Below 40 cols, print a one-line
error (`Terminal too narrow (need ≥40 cols, got N). Quit and resize.`)
and exit non-zero — do NOT fall back to stdout, because the user
explicitly asked for the TUI and silent stdout fallback would be
surprising.

### Drill-down panel (one-step flow)

On Enter, replace the main list with a session list for the selected row.
The initial `bucket_idx` is the row's highest non-zero bucket (the spike).
`h`/`l` moves between buckets without leaving drill-down; `j`/`k` scrolls
sessions within the current bucket.

**While drill-down is open, `Tab`, `d`, `w`, and `Enter` are no-ops** (a
status line shows `Esc to back`). Closing drill-down with `Esc` returns to
the trend list, where those keys are live again. This avoids the
`sessions_by_bucket` cache desync — the pre-computed sessions match the
dimension+bucket_by that were active when Enter was pressed, so changing
either while drill-down is open would lie. Close, switch, re-open.

```
┌─ coding/jira-123 | week of 2026-06-09 (5h 30m) — Esc to back ──┐
│   (← week 2026-06-02 » week 2026-06-09 » week 2026-06-16 →)    │
│                                                                  │
│  Mon 06-09  09:00–11:30   2h 30m   #em01  [link]                │
│  Tue 06-10  14:00–15:00   1h 00m   #em01                        │
│  Wed 06-11  10:00–12:00   2h 00m   #em11                        │
│                                                                  │
├──────────────────────────────────────────────────────────────────┤
│ h/l bucket  j/k session  o open link  Esc back                   │
└──────────────────────────────────────────────────────────────────┘
```

`Esc` closes drill-down and returns to the trend list. `q` always quits
(even from drill-down). `o` on a session with a `link` invokes the
existing `open_link` / `open_in_nvim` helpers that history_view.rs:1
already imports — no new infra.

### Keybindings (consistent with existing wdttg TUIs)

| Key | Action |
|-----|--------|
| `j` / ↓ | move selection down |
| `k` / ↑ | move selection up |
| `Tab` | cycle dimension: Task → Tag → Quadrant → SplitAttention → Task |
| `d` | bucket by day |
| `w` | bucket by week |
| `Enter` | drill into selected row; opens at its highest non-zero bucket |
| `h` / `l` | (drill-down only) move to previous/next bucket |
| `o` | (drill-down only) open the selected session's link |
| `Esc` | close drill-down (or quit if no drill-down open) |
| `q` | quit |

There is no in-TUI period cycling key. Period comes from the CLI
(`wdttg report trend 12w`); re-run to change it. This matches `timeline
[date]` and `report history --period`, both of which take their period as
a launch parameter.

### stdout fallback (--no-prompt)

```rust
fn handle_report_trend(
    period: &str,
    by: &str,
    by_tag: bool,
    top: usize,
    no_prompt: bool,           // NEW param, threaded from main.rs:1677
    db: &Arc<Database>,
) -> Result<(), String> {
    let session_service = SessionService::new(Arc::clone(db));
    let (start, end) = parse_period(period)?;
    let sessions = session_service
        .get_split_times(start, end)
        .map_err(|e| e.to_string())?;

    if sessions.is_empty() {
        println!("No sessions found for period: {}", period);
        return Ok(());
    }

    if no_prompt {
        // Existing stdout path stays here, refactored to call the shared
        // compute_trend_buckets() helper. Behavior byte-identical.
        let task_tags = if by_tag { Some(session_service.get_task_tags()?) } else { None };
        print_trend_stdout(&sessions, task_tags, start, end, by, by_tag, top)
    } else {
        // New default: open the TUI.
        let task_tags = session_service.get_task_tags().map_err(|e| e.to_string())?;
        let starting_dim = if by_tag { TrendDimension::Tag } else { TrendDimension::Task };
        let bucket_by = match by { "day" => BucketBy::Day, _ => BucketBy::Week };
        let view = TrendView::new(sessions, task_tags, start, end, starting_dim, bucket_by, top);
        view.run().map_err(|e| e.to_string())
    }
}
```

**Shared pure function** — both paths call:

```rust
/// Buckets sessions by dimension and bucket_by. Returns (items, totals)
/// where items is sorted by total desc and truncated to `top`. Each item
/// is (name, Vec<seconds_per_bucket>).
fn compute_trend_buckets(
    sessions: &[SessionSplitTime],
    task_tags: Option<&HashMap<i64, Vec<String>>>,
    dimension: TrendDimension,
    bucket_by: BucketBy,
    start: NaiveDate,
    end: NaiveDate,
    top: usize,
) -> Vec<(String, Vec<i64>)> { ... }
```

This preserves the current sentinel-pattern behavior at main.rs:1267-1297
(the `__total__` row, removed at the end), the `dedup()` on bucket dates
(main.rs:1254), and the sort-then-truncate at main.rs:1299-1307.

## Open Questions

1. **Should SplitAttention sparkline normalize?** Overlap seconds are
   typically much smaller than total seconds. Showing raw overlap sparkline
   per task is honest but the bars are tiny. **Resolved: keep per-row
   scaling (current `render_sparkline` behavior at main.rs:1178 already
   does this). It shows the shape of the trend, which is what matters;
   absolute overlap is in the duration column.**

2. **Period/bucket UI placement.** Two viable shapes: (a) inline header
   `Trend: Task | 8w weekly | ...` (compact, current proposal), or (b)
   a dedicated status line under the title showing all cyclable states.
   **Resolved: (a) — header stays scannable, footer hints document the
   keys.**

3. **Phased ship or all-at-once?** Reviewer flagged that drill-down is
   ~150 lines on top of the dimensions and TUI shell. **Resolved: ship
   together.** Without drill-down, the "spot the spike, understand why"
   loop doesn't close — the TUI would be a prettier stdout. The whole
   point is exploration, and drill-down is what makes exploration pay off.
