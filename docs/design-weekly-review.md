# Design: Guided Weekly Review with Control Loop

Generated by /office-hours on 2026-06-13
Branch: main
Repo: tta/wdttg
Status: APPROVED
Mode: Builder

## Problem Statement

WDTTG tracks time with Eisenhower Matrix quadrant support, but tracking without
reflection is just data collection. The missing piece is a guided weekly review
that closes the loop: what you intended (targets) vs what actually happened
(tracked time) vs what you'll change (adjustment).

Every existing weekly review tool starts with a blank page: "write down what you
did this week." WDTTG already has the answer. The review should be data-driven,
not template-driven. No CLI tool connects the three vertices: (1) actual
behavioral data from time tracking, (2) priority framework (EM quadrants), and
(3) structured reflection. This triangle is unconnected by any existing tool.

## What Makes This Cool

Two signals no competitor can produce:

1. **Split-Attention Metric.** WDTTG's `get_split_times()` already computes
   `overlap_seconds` -- when a background task ran during foreground work. That
   overlap IS split attention, measured. "This week you multitasked 8.5 hours.
   Task X was running under 4 of your deep-work sessions." No template tool
   can produce this because no other tracker has the background/foreground model.

2. **Quadrant Budget vs Actual.** Like hledger's `--budget` report: planned vs
   actual per category with delta indicators. "You targeted 60% Schedule, you
   got 35%." The gap between intention and reality is the behavior-change moment.

The control loop: stored intention (targets) -> measured reality (tracked time)
-> visible gap (delta) -> adjusted intention (new targets). This turns WDTTG
from a stopwatch into a steering wheel.

## Constraints

- **No new runtime dependencies.** The tool is dependency-free at runtime
  (SQLite + Rust stdlib). The review must use structured comparisons, not AI/LLM.
- **Terminal-native.** Must work as a TUI with vim keybindings, consistent with
  existing components (j/k navigation, Ctrl+n/p in search, ratatui-based).
- **Must fix timezone bug first.** `get_date_range()` treats local date
  boundaries as UTC timestamps, silently corrupting report data for non-UTC
  users. The review depends on accurate data.
- **Single-binary architecture.** No daemon, no IPC, no background process.
  The review is a command (`wdttg review`) that opens a TUI, same as
  `wdttg timeline`.
- **SQLite migrations must remain idempotent.** New tables use
  `CREATE TABLE IF NOT EXISTS` in the existing `execute_batch` block in
  `run_migrations()` (db.rs:120-168). No column-existence checks needed for
  new tables -- those are only for `ALTER TABLE ADD COLUMN`.

## Premises

1. Weekly review is the missing piece that makes time tracking meaningful --
   without reflection, the data is just a log, not a behavior change tool.
2. A data-driven review (from actual tracked time) is fundamentally different
   from a template-driven review (blank page), and this is WDTTG's unique
   advantage.
3. The review should be a TUI experience, not just text output -- interactive,
   keyboard-driven, visually rich.
4. The review doesn't need AI/LLM -- structured comparisons are more useful
   than AI coaching prose, and keep the tool dependency-free.
5. Existing timezone bugs must be fixed first because the review depends on
   accurate data.

## Cross-Model Perspective

An independent Claude subagent (fresh context, no conversation history) reviewed
the problem, answers, premises, and landscape findings:

- **Key insight:** The split-attention metric (`overlap_seconds` in
  `get_split_times()`) is a unique signal hiding in existing code. No other
  time tracker can produce this because none have the background/foreground
  model. This should be a headline feature of the review.
- **Mental model:** Steal the budget-vs-actual framing from hledger/ledger-cli,
  not from Notion/Todoist templates. Delta language ("40% over on Q4") is more
  actionable than pie charts.
- **Architecture:** The feature spine is target storage and reconciliation, not
  stats display. If the weekend only produces one new table, it should be
  `weekly_targets` (intention). Everything else (quadrant times, split times)
  already exists to fill the "reality" side.
- **Cold start:** First-time users have no prior targets. Need sensible defaults
  (80% Q2 / 20% Q1 from README) or a guided first-run.

## Approaches Considered

### Approach A: Delta Dashboard (Minimal)

One TUI screen showing week-over-week deltas for quadrants + split-attention
summary. No new tables, no target storage. Composes existing methods
(`get_quadrant_time`, `get_split_times`) into a new view.

- **Effort:** S (1 weekend)
- **Risk:** Low
- **Pros:** Ships fast, validates concept
- **Cons:** Without targets, it's just a prettier report. The "should have gone"
  half of the thesis isn't tested. Not a control loop -- just a dashboard.

### Approach B: Control Loop Review (CHOSEN)

Full review with target storage, interactive target setting, quadrant
budget-vs-actual, split-attention panel, and review notes persistence.

- **Effort:** L (2-3 weekends)
- **Risk:** Medium (new migration, new TUI interactions)
- **Pros:** Closes the intention -> reality -> gap -> adjust loop. Split-attention
  panel uses data no competitor has. Review notes create a reflection journal.
- **Cons:** More work: new migration, new service methods, new TUI interactions.

### Approach C: Delta Dashboard + Forward Path

Start minimal but architect the service layer for future target storage.

- **Effort:** M (1.5 weekends)
- **Risk:** Medium (over-abstraction risk)
- **Pros:** Validates before investing
- **Cons:** YAGNI risk -- abstracting for future extensibility without building it.

## Recommended Approach

**Approach B: Control Loop Review.** The control loop IS the product. Without
targets, it's a prettier report. The gap between intention and reality is what
makes people change behavior.

### Architecture

```
db.rs
  + weekly_targets table        (in run_migrations execute_batch)
  + weekly_reviews table        (in run_migrations execute_batch)

services/review_service.rs (new)
  ReviewService {
    db: Arc<Database>
  }
  Methods:
    + get_week_summary(week_start: NaiveDate) -> Result<WeekSummary>
    + get_split_attention(week_start: NaiveDate) -> Result<(i64, Vec<SplitTask>)>
    + set_target(week_start: NaiveDate, quadrant: EmQuadrant, target_minutes: i64)
    + get_targets(week_start: NaiveDate) -> Result<Vec<QuadrantTarget>>
    + save_review(week_start: NaiveDate, notes: &str)
    + get_review_history(limit: usize) -> Result<Vec<WeeklyReview>>
    + get_8week_trend(week_start: NaiveDate) -> Result<Vec<WeekSummary>>

  Upsert semantics for set_target:
    INSERT INTO weekly_targets (week_start, em_urgent, em_important, target_minutes)
    VALUES (?, ?, ?, ?)
    ON CONFLICT (week_start, em_urgent, em_important)
    DO UPDATE SET target_minutes = excluded.target_minutes

  Upsert semantics for save_review:
    INSERT INTO weekly_reviews (week_start, notes)
    VALUES (?, ?)
    ON CONFLICT (week_start)
    DO UPDATE SET notes = excluded.notes

  Percentage computation (per quadrant):
    Guard: if sum == 0 { return 0.0 }  // prevents NaN from 0/0
    target_pct = target_minutes / sum(all target_minutes for week) * 100
    actual_pct = actual_seconds / sum(all actual_seconds) * 100
    delta_pct  = actual_pct - target_pct

models/review.rs (new)
  // All time fields in SECONDS for consistency with existing session_service methods
  // Uses HashMap, not array -- EmQuadrant has no clean as-usize mapping
  WeekSummary {
    quadrant_actuals: HashMap<EmQuadrant, i64>,  // seconds
    quadrant_targets: HashMap<EmQuadrant, i64>,  // seconds (from target_minutes * 60)
    total_seconds: i64,                          // foreground sessions only (no background inflation)
    split_attention_seconds: i64,
    top_split_tasks: Vec<SplitTask>,             // sorted desc by overlap_seconds
    week_start: NaiveDate,                       // for trend labeling
  }

  SplitTask {
    name: String,
    overlap_seconds: i64,
    session_count: usize,             // number of foreground sessions affected
  }

  // QuadrantTarget stored as minutes in DB, converted to seconds in WeekSummary
  QuadrantTarget {
    week_start: NaiveDate,
    quadrant: EmQuadrant,
    target_minutes: i64,
  }

  WeeklyReview {
    week_start: NaiveDate,
    notes: String,
    created_at: DateTime<Utc>,
  }

  // 8-week trend is Vec<WeekSummary> -- reused, no new type

ui/review.rs (new)
  ReviewView {
    summary: WeekSummary,
    trend: Vec<WeekSummary>,          // 8 weeks, oldest first
    targets: Vec<QuadrantTarget>,
    selected_row: usize,              // within active section
    active_section: ReviewSection,    // QuadrantTable / SplitAttention / Notes
    week_start: NaiveDate,
    // Inline editing state (only one edit active at a time)
    editing: Option<EditState>,
  }

  enum ReviewSection { QuadrantTable, SplitAttention, Notes }

  struct EditState {
    buffer: String,
    cursor: usize,
    kind: EditKind,                   // Target(quadrant) or Notes
  }

  enum EditKind { Target(EmQuadrant), Notes }

  // Keybindings:
  //   Tab          -- cycle active_section (Quadrant -> Split -> Notes -> Quadrant)
  //   j/k          -- navigate rows within active section
  //   t            -- start target edit on selected quadrant row
  //   n            -- start notes edit
  //   Enter        -- in target edit: save target, exit edit mode
  //                   in notes edit: insert newline
  //   Ctrl+S       -- in notes edit: save notes, exit edit mode
  //   Esc          -- cancel edit, discard buffer
  //   h/l          -- prev/next week (not in edit mode)
  //   q            -- quit (not in edit mode)

  Result enum:
    ReviewResult::Closed
    ReviewResult::SetTarget(EmQuadrant, i64)  // quadrant, minutes
    ReviewResult::SaveNotes(String)
```

### Database Schema

```sql
-- weekly_targets: stores intention per quadrant per week
-- Added in run_migrations() execute_batch block (db.rs)
CREATE TABLE IF NOT EXISTS weekly_targets (
    week_start TEXT NOT NULL,           -- ISO date (Monday of the week)
    em_urgent INTEGER NOT NULL CHECK (em_urgent IN (0, 1)),
    em_important INTEGER NOT NULL CHECK (em_important IN (0, 1)),
    target_minutes INTEGER NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (week_start, em_urgent, em_important)
);

-- weekly_reviews: stores free-text review notes per week
CREATE TABLE IF NOT EXISTS weekly_reviews (
    week_start TEXT NOT NULL,
    notes TEXT,
    created_at TEXT NOT NULL DEFAULT (datetime('now')),
    PRIMARY KEY (week_start)
);
```

**Target write:** Upsert via `INSERT ... ON CONFLICT DO UPDATE` (see Architecture).
**Cold-start defaults:** Virtual only -- not persisted. If `get_targets()`
returns empty, the TUI displays suggested targets (20% DoFirst, 60% Schedule,
10% Delegate, 10% Eliminate) as greyed-out rows. User must press `t` to persist
real targets. No magic database rows on first run.

**Week-start computation:** `week_start = today - days_since_monday` where
`days_since_monday = today.weekday().num_days_from_monday()`. Stored as
`NaiveDate`, formatted as `YYYY-MM-DD` in SQL.

### CLI Integration

```
wdttg review              # Open interactive weekly review TUI (default: this week)
wdttg review --week N     # Review ISO week N of current year
wdttg review --date YYYY-MM-DD  # Review the week containing this date
```

`--week N` uses current year. For cross-year weeks (e.g. week 1 of 2027 may
start Dec 28 2026), the ISO 8601 week date handles this correctly via
`NaiveDate::from_isoywd()`.

No `--month` scope for now -- the control loop works on weekly cadence.
No `--no-prompt` mode -- if scripting output is needed later, add a
`--json` flag. Keep scope minimal for first implementation.

### Implementation Order

1. **Fix timezone bug in `get_date_range()`** (prerequisite -- review depends
   on accurate data). Convert local date boundaries to UTC properly using
   `Local.from_local_datetime().single().unwrap_or(fallback)` pattern.

2. **Fix DST panic risk** in `get_day()` and `get_day_with_gaps()`. Replace
   `.single().unwrap()` with `.earliest().unwrap_or_else(|| fallback_datetime)`
   where `fallback_datetime` is constructed from the NaiveDateTime + a known
   valid offset. `from_local_datetime()` returns `MappedLocalTime` which has
   `.earliest()` (for ambiguous fall-back times) and `.single()` (for normal
   times). Same fix in `time_parser.rs:167-168`.

3. **Add database migration** for `weekly_targets` and `weekly_reviews` tables.
   Append both `CREATE TABLE IF NOT EXISTS` statements to the existing
   `execute_batch` string in `run_migrations()` (db.rs).

   **All ReviewService queries must use local-to-UTC conversion for date
   boundaries** -- same pattern as the fixed `get_date_range()`. Week start/end
   `NaiveDate` values are converted to local midnight `NaiveDateTime`, then to
   `DateTime<Local>`, then to UTC timestamps for SQL parameters. This prevents
   the timezone bug from recurring in the new code.

4. **Build `ReviewService::get_week_summary()`** with its own SQL queries.
   Cannot call `get_quadrant_time()` directly because it has
   `end_time IS NOT NULL` (excludes active sessions). Instead, write a query
   that uses `COALESCE(s.end_time, datetime('now'))` for duration:

   ```sql
   SELECT t.em_urgent, t.em_important,
          SUM(CAST(strftime('%s', COALESCE(s.end_time, datetime('now'))) AS INTEGER)
              - CAST(strftime('%s', s.start_time) AS INTEGER)) AS total_secs
   FROM sessions s JOIN tasks t ON s.task_id = t.id
   WHERE s.start_time >= ?1 AND s.start_time < ?2
     AND s.is_background = 0
   GROUP BY t.em_urgent, t.em_important
   ```

   **Must zero-fill all 4 quadrants** -- iterate all EmQuadrant variants and
   default to 0 seconds if missing from query results.

   **Data flow:** `get_week_summary` must internally call `get_split_attention`
   to populate `split_attention_seconds` and `top_split_tasks` fields. Both
   are populated before returning the `WeekSummary`.

5. **Build `ReviewService::get_split_attention()`** with its own SQL query.
   Cannot reuse `get_split_times()` directly because it doesn't expose
   per-task session counts. Instead, query for background/foreground overlaps:

   ```sql
   -- Foreground (a) x Background (b) overlap pairs.
   -- Asymmetry is enforced: a.is_background=0, b.is_background=1.
   -- COALESCE handles active sessions (end_time IS NULL).
   SELECT bt.name AS bg_task,
          SUM(CAST(strftime('%s', MIN(COALESCE(a.end_time, datetime('now')), COALESCE(b.end_time, datetime('now')))) AS INTEGER)
              - CAST(strftime('%s', MAX(a.start_time, b.start_time)) AS INTEGER)) AS overlap_secs,
          COUNT(*) AS session_count
   FROM sessions a JOIN sessions b
     ON a.start_time < COALESCE(b.end_time, datetime('now'))
     AND b.start_time < COALESCE(a.end_time, datetime('now'))
   JOIN tasks bt ON b.task_id = bt.id
   WHERE a.start_time >= ?1 AND a.start_time < ?2
     AND b.start_time >= ?1 AND b.start_time < ?2
     AND a.is_background = 0
     AND b.is_background = 1
   GROUP BY bt.name
   ORDER BY overlap_secs DESC
   ```

   This produces `SplitTask { name, overlap_seconds, session_count }` directly.
   No double-counting: the `a.is_background = 0 AND b.is_background = 1` filter
   ensures each (foreground, background) pair matches exactly once.
   **Total split-attention** (`i64`) = sum of all rows' `overlap_secs` in Rust
   (no LIMIT in SQL -- slice to top 5 in Rust after computing total).

6. **Build `ReviewService::get_8week_trend()`** -- calls `get_week_summary()`
   for each of the 8 weeks ending at current `week_start`. Returns
   `Vec<WeekSummary>` oldest-first. The TUI renders one sparkline character
   per week per quadrant row.

7. **Build `ReviewView` TUI** -- quadrant budget vs actual table with
   sparklines, split-attention panel, review notes display.

8. **Add target setting** -- `t` key on a selected quadrant row opens an
   inline number input prompt (same pattern as `edit_form.rs` inline editing).
   User types a number (interpreted as minutes) and presses Enter.
   Calls `set_target()` which upserts to `weekly_targets`. Percentages are
   recomputed live from the new totals.

9. **Add review notes** -- `n` key opens a multi-line text input area in the
   TUI (inline, not `$EDITOR`). Consistent with terminal-native vision.
   Calls `save_review()` which upserts to `weekly_reviews`.

10. **Add week navigation** -- `h`/`l` keys navigate to prev/next week.
    Reloads all data for the new `week_start`.

11. **Add CLI command** `wdttg review` in `cli.rs` and `main.rs`.

### Edge Cases

1. **Sessions spanning midnight.** A session from 23:30 to 01:00 next day
   currently belongs to the day it started (per `get_day()` behavior). The
   review uses the same `get_date_range()` boundary. Sessions spanning a
   week boundary (Sunday 23:00 to Monday 01:00) are attributed to the week
   containing `start_time`. This is consistent with existing report behavior.
   Documented, not "fixed" -- splitting sessions would change existing
   semantics and is out of scope.

2. **Active/running sessions.** A session with `end_time IS NULL` is still
   running. The review includes it using `COALESCE(end_time, datetime('now'))`
   in the duration calculation. Shows a `*` indicator in the TUI to flag
   that the week's data includes a still-running session.

3. **Empty week.** If no sessions exist for the week, the TUI shows all
   quadrants at 0%, split-attention at 0, and displays "No sessions tracked
   this week." Review notes can still be saved.

4. **DST transition.** After fix #2, DST transitions no longer panic.
   A 23-hour or 25-hour day during DST is handled correctly -- the duration
   math uses actual timestamps, not day boundaries.

5. **Database errors.** All `ReviewService` methods return `Result<T>`.
   The TUI catches errors and displays them inline (same pattern as existing
   TUI error handling in `timeline.rs`).

## Open Questions

1. **Sparkline time range.** Show raw seconds (total tracked time per quadrant)
   for the 8-week trend. Split-attention is shown as a separate metric in its
   own panel, not mixed into quadrant sparklines.

2. **Target granularity.** Per-quadrant percentages only for now. Per-tag
   targets ("max 2h/week on admin") could be a future enhancement but adds
   significant schema and UX complexity.

3. **Multi-week review history.** Not in scope for first implementation.
   The `h`/`l` week navigation lets you browse past weeks' data. Browsing
   past review *notes* across weeks is a natural follow-up command
   (`wdttg review --history`) but deferred.

4. **Obsidian export.** Deferred. The review notes are stored in SQLite.
   A future `wdttg review --export` command could emit markdown for Obsidian
   vaults, reusing the existing `clipboard.rs` note-path utilities. Not in
   scope for the control loop feature.

## Success Criteria

- The weekly review TUI opens in under 100ms (consistent with other TUI commands).
- Quadrant budget vs actual shows correct deltas (validated against manual
  calculation).
- Split-attention metric correctly aggregates overlap_seconds from
  get_split_times.
- Target setting persists across sessions and is displayed in subsequent reviews.
- Review notes are saved and viewable in past reviews.
- The timezone bug is fixed and reports show correct data for non-UTC users.
- After using the review for 2 weeks, the builder can answer: "Did seeing the
  split-attention metric and quadrant gap change my behavior?"
